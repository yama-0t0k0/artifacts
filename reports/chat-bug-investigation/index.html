03

Critical 3件 — 何が起きているか

いずれも「チャットが使えない」レベルの不具合。図は現状の壊れた流れを示す。

C-1

チャット画面のルート未登録 — FABを押しても何も起きない

ROUTES.TALK_LIST / ROUTES.P2P_CHAT は定数として定義され、TalkListScreen / P2PChatScreen も実装・テスト済み。しかし Stack.Screen として登録している Navigator が個人アプリ・法人アプリのどちらにも存在しない。React Navigation は未登録ルートへの navigate を console エラーだけで握り潰すため、catch にも落ちずユーザーには完全な無反応に見える。

ConciergeFAB.js:113AppNavigator.js（登録なし）corporate App.js:79-110（登録なし）CorporateConnectionScreen.js:94
C-2

既定LLMプロバイダ (gemini) が Function Calling 非対応 — 操作代行が全滅

gemini の buildBody(messages, systemPrompt) は第3引数 tools を受け取らずツール定義を黙って破棄。さらに role マッピングが assistant→model / それ以外→user しかなく、role:'tool' の実行結果や tool_calls が不正な形で送信され、ツール実行後の再リクエストで会話が破壊される。EXPO_PUBLIC_LLM_PROVIDER 未設定の既定構成で発生する。

C-3

初回メッセージ送信でユーザーの発言が消える — 購読切替レース

新規トピックの初回送信で handleSend がトピック作成 → setActiveTopicId を実行すると、メッセージ購読 effect が再実行される。serverTimestamp 確定前の空 snapshot が Optimistic 表示中の一時メッセージ (temp_...) を welcome だけの配列で上書きし、送ったはずのメッセージが画面から消える。

05

根本原因の分析

33件の不具合は、個別ミスではなく5つの構造的な原因に収束する。

🔌

① 画面は作ったが結線していない

TalkListScreen / P2PChatScreen は実装・テスト済みなのに Navigator 登録工程が抜けている。Issue #643（SupportScreens 導入の契機）と同型の「共通画面のルート登録漏れ」再発パターン。

🧩

② プロバイダ抽象化の非対称性

Function Calling 対応が qwen / ollama / openai だけに後付けされ、既定の gemini と forAgentBackend が取り残された。buildBody のシグネチャ不一致をテストが検出していない。

⚡

③ Optimistic UI の境界設計が未定義

「一時IDとサーバdoc IDの対応付け」「購読切替時の一時メッセージ保護」という基本設計が欠落。C-3 / H-2 / M-7 は同根で発生している。

🌐

④ Web配信前提の不徹底

Alert.prompt（iOS専用）・多ボタンAlert（Web no-op）・ローカルURI画像など、iOSネイティブ前提の実装が混入。Expo Web ビルドは主要配信チャネルなのに検証から漏れている。

🔐

⑤ セキュリティ設計の後回し

APIキー・会話本文のログ出力、バックエンドAPIの無認証呼び出し（uid 自己申告）、rules の update/delete 欠落。攻撃前提の設計レビューが行われていない。

P0-1 チャットルートの共通登録ファクトリ

→ C-1

SupportScreens.js 方式を踏襲した renderChatScreens(Stack) を新設し、TalkList / P2PChat の登録を1関数に集約。individual / corporate 両 Navigator に組み込む。再発防止として「ROUTES の全値が Navigator に登録済みか」を検査する jest テストと、FAB→トーク一覧の E2E スモークを追加する。

P0-2 全プロバイダの Function Calling 統一

→ C-2 / M-9

全プロバイダで buildBody(messages, systemPrompt, tools) の3引数シグネチャを強制。gemini は OpenAI 形式 tools を functionDeclarations へ、role:'tool' を functionResponse part へ、tool_calls を functionCall part へ変換するアダプタを実装し、レスポンスは OpenAI 互換 {content, toolCalls} に正規化して返す。

P0-3 Optimistic UI の再設計 — doc ID 先行採番 + pending キュー

→ C-3 / H-2 / M-7

doc(collection(db,'chat_messages')) で ID を addDoc 前に確定させ、pending Map に登録してから setDoc。onSnapshot はサーバ配列と pending をマージ表示し、空 snapshot でも pending があれば welcome にリセットしない。一時IDとサーバIDの乖離が構造的に消えるため、フィードバックの messageId 問題 (H-2) も同時に解決する。

P0-4 onSnapshot エラーハンドリング標準化

→ H-1

3購読すべてにエラーコールバックを追加し、failed-precondition（インデックス構築中）と権限エラーを区別した再試行ボタン付きバナー ListenerErrorBanner を共通コンポーネント化する。P1 のインデックス追加デプロイ時の保険にもなる。

P1-1 フィードバック系の再設計

→ H-2 / H-3 / M-15
  • 自然キー化: chat_feedback の doc ID を messageId に固定し setDoc(merge) で再評価は上書き — 重複増殖を根絶
  • クエリ修正: orderBy('createdAt','desc') + limit(20) に変更し、(uid ASC, createdAt DESC) の複合インデックスを追加
  • rules: chat_feedback に所有者の update / delete を許可
  • DPO用: systemPromptSnapshot の空文字固定をやめ実プロンプトを保存

P1-2 トピック管理のクロスプラットフォーム化

→ H-4 / H-5 / M-5
  • TopicActionSheet 新設: OS ネイティブ Alert を全廃し、RN Modal ベースのボトムシート + 入力モーダルで全プラットフォーム同一実装に
  • 並び順: isPinned 降順 → updatedAt 降順 のクライアントソート
  • カスケード削除: 配下の chat_messages / chat_feedback を 400件ずつバッチ削除（将来はバックエンド onDelete トリガへ移行）

P1-3 P2P画像の Storage アップロード実装

→ H-8

Storage ルールは participants のみ read/write 可・5MB 上限・image/* 限定。失敗時は「再送」ボタン付きエラーバブルに変える。

P1-4 未読・既読の一貫設計

→ M-11 / M-12 / M-1 / M-2
  • 未読の単一情報源を users/{uid}/unread_chats に統一。FAB バッジは notifications 購読をやめ UnreadContext.totalUnread を参照（ログインタイミング問題も同時解消）
  • メッセージ単位の isRead を廃止し、ルーム単位の lastReadAt 方式へ移行（rules は readReceipts のみ participants に更新許可）
  • 入室中の新着は useIsFocused + debounce で自動リセット

P1-5 バックエンドAPI認証

→ H-7 / L-6

authorizedFetch ヘルパーを新設し、Firebase ID トークンを Authorization: Bearer で送付 + 30秒タイムアウト。Dart 側にトークン検証ミドルウェアを追加し、uid はトークンから導出（ボディの userId 自己申告を廃止）。

07

実装ロードマップとテスト計画

🧪 テスト計画

  • 単体 (jest): 全プロバイダ × tools のボディ生成スナップショット / 初回送信の表示維持 / feedback doc ID = message ID / TopicList ソート
  • ルール (emulator): chat_feedback の所有者 update・delete / readReceipts の participants 限定 / Storage の participants 限定 read
  • E2E (playwright, Web): FAB → TalkList → P2P 送受信 / 初回送信 → 評価 → リロード後保持 / トピック CRUD が Web で成立
  • 実機 (iOS/Android): 画像の相互表示 / プッシュ通知 (chat_trigger_service)

✅ 調査で確認できた正常動作

  • chat_messages の複合インデックス (uid, topicId, createdAt) は定義済みでクエリと整合
  • escapeNonAscii のマルチバイト対策は ChatLM.md 4.1 の知見どおり実装済み
  • Ollama アダプタの tool_calls 正規化 (object→string) は適切
  • chat_rooms / unread_chats の participants ベース読み取り制御は概ね妥当
  • chat_trigger_service.dart のプッシュ通知フローは妥当（pushToken 未登録時は正常スキップ）
⚠️
リリース手順の注意: chat_feedback の複合インデックスはコード修正より先にデプロイすること（H-3 修正クエリが failed-precondition になるため）。firestore.rules の変更はクライアント修正と同一リリースで適用。gemini のヘッダ認証移行は .env 変更不要（キーの渡し方のみ変更）。
