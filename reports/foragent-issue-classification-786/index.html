1. 分類の軸

forAgent は Modular Monolith（Monorepo）で、アプリ実体は apps/ だけに閉じていません。 Issue 本文の「変更ファイル」節に列挙されたパスを実際のディレクトリ構造へ突き合わせ、次の 6 レイヤーへ分類しています。 図は今回の対象期間で実際に増減したものを反映しています（apps/admin_app/node_backend は前回期間の #771 で撤去済み、 infrastructure/qwen_serving と 4 つのコレクションが今回追加されました）。

レイヤー区分の定義（1 Issue が複数レイヤーに跨がることは普通にある）

  • フロントエンド — apps/*/expo_frontend、apps/lp_app の画面・配線
  • バックエンド — apps/functions（Cloud Functions）、apps/backend（Dart / Cloud Run）
  • 共通モジュール — shared/ 配下。フロント共通コンポーネント・ドメインサービス・共通ロジック
  • データ層 — infrastructure/firebase、infrastructure/qwen_serving、tests/security_rules、スキーマ移行
  • CI・リリース基盤 — scripts/、githooks/、.github/workflows、tests/、ビルド設定、.claude/launch.json
  • ドキュメント・仕様 — docs/、spec/、DESIGN.md、.claude/skills/

2. 9 つの作業テーマと、その連鎖

#786 以降の 39 件も、独立したタスクの寄せ集めではありません。矢印は時系列ではなく因果で、 ひとつの修正が次の問題を露出させる形で繋がっています。どのアプリの Issue かを読むときは、 この連鎖のどこに位置するかを併せて見ると背景が掴めます。

8. 要判断・未対応と、申し送り

今回の 39 件のうち、修正コミットを伴わない／実行が保留されているものが 3 件あります。 これに加えて、Issue としては閉じていないが作業の中で明示的に「未対応」と記録された申し送りを併記します。

要判断・未対応（3 件）

  • #791 SuitabilityService の削除提案 — プロダクトコードからの参照はゼロで、コード自身が「Simplified for prototype」と述べている。本マップ作成時点でも core/domain/ 配下に現存を確認した。誤って呼ばれると適合度が固定値 85 からの加減算になり、成長ゾーン優遇・オーバースペック減点というマッチング哲学が反映されない。テストが付いているせいで「動く実装」に見えるのが厄介な点。
  • #806 check_spec_compliance.js の判定粒度 — accepts が実質「spec/ のどこかが変わっていれば OK」と同義になっており、無関係な仕様書を 1 本追加するだけで警告が消えることを実データで再現済み。コード修正は未実施で、#810 の時点でも未着手のまま。
  • #824 Production Config Audit の権限付与 — 監査 13 件中 4 件が「検査自体が失敗」しており、原因は本番設定の不備ではなく CI の SA（github-actions-deployer@）の権限不足。付与するのは読み取り専用ロール 3 つだが、本番 IAM の変更のためユーザー実行待ち。付与用の gcloud コマンドまでスクリプトが出力する形にしてある。

申し送り（Issue 本文に「未対応」と明記されたもの）

  • #802 — EngineerSearchScreen は App.js から未接続のままで Star 機能が使えない（前提だったルール欠落と companyId ハードコードは解消済み、残るのは接続のみ）。companyMembers.js / registerCompany.js は未デプロイ。
  • #817 — features/settings/ は実装があっても App.js から未配線。ProfileEditScreen.tsx は保存処理が setTimeout の疑似保存のままで、配線する前に保存処理を実装すべき旨をコードと docs の両方に明記した（ProfileVisibilityScreen が「見せかけの設定」だった問題の再発予告）。
  • #820 — dashboardStyles のインラインリテラルが 75 件残る。うち borderRadius: 10 の 2 件は DESIGN.md §3 への明確な違反だが、是正は見た目の変更を伴うため据え置き。width: 34（アイコンの円）や height: 1（区切り線）のように余白スケールへ丸めてはならない構造的な値も混在する。
  • #824 — jest.config.js の firebaseConfig スタブへの moduleNameMapper が実際には効いていない（babel-plugin-module-resolver が先に相対パスへ書き換えるため一致しない）。テスト中に実 firebaseConfig が評価されることをプローブテストで実測済み。
  • #825 — 原則に照らすと 職歴（社名）・求職の有効期間・性別・学歴詳細 は「誰にでも見せてよい」水準ではないが、マッチング成立に必要なため現時点では公開側に置いている。真に公開／会員限定／本人のみ の 3 層への分割が必要。
  • #827 — isHumanAuthenticated() から匿名ユーザーを除外する。保留の理由だった「実行すると既存画面が全部壊れる」という前提は、匿名を作る経路が消えたことで解消した。
  • #819 — MODEL_ID 変更時の再デプロイ動作は未検証。評価は baseline=candidate の自己比較のままで、実際の DPO 学習後モデルとの比較は dpo_pairs が 200 件以上たまってから。

9. この分類の作り方

Issue 番号を変えて同じ集計を繰り返せるよう、判定は次の順序で行っています。

  • ① 対象の抽出 — gh issue list --repo yama-0t0k0/forAgent --state all --json number,title,labels,body で取得し、指定番号以降を対象にする。タイトルが chore: Agent ブランチ最新化と same へのマージ・main 最新化 で始まるものはブランチ同期作業として除外（今回は 5 件）。
  • ② パス抽出 — Issue 本文の「変更ファイル」節に列挙されたパスを取り出す（節が無い場合は本文全体から）。
  • ③ アプリ／レイヤー判定 — apps/<app>/expo_frontend → そのアプリのフロントエンド、apps/functions → Cloud Functions、shared/** → 共通モジュール、infrastructure/ と tests/security_rules → データ層、scripts/・githooks/・.github/ → CI・リリース基盤、docs/・spec/ → ドキュメント・仕様、という先頭一致で写像する。
  • ④ 全件の本文を読んで補正 — ③だけでは取りこぼす。今回は 39 件中 14 件（約 36%）がスクリプトの「手読みが必要」判定に該当した。内訳は「変更ファイル節を持たない調査報告のみの Issue」（#791 / #806 / #829 など）、「forAgent 側にコミットが無い作業」（#786 / #788 / #826）、「本文の記述形式が定型と異なる Issue」。前回の 10/64 件（約 15%）より比率が上がっており、スクリプトの出力をそのまま成果物にはできないという前提は今回も変わらなかった。
  • ⑤ リンクの実在検証 — 表に載せた docs/ spec/ DESIGN.md へのリンク全件について、git cat-file -e origin/Agent:<path> で実在を確認している。実在しないドキュメントへのリンクは、リンクが無い状態より有害（読者を存在しない根拠へ誘導するため）。
