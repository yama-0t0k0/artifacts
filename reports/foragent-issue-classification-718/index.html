1. 分類の軸

forAgent は Modular Monolith（Monorepo）で、アプリ実体は apps/ だけに閉じていません。 Issue 本文の「変更ファイル」節に列挙されたパスを実際のディレクトリ構造へ突き合わせ、次の 6 レイヤーへ分類しています。

レイヤー区分の定義（1 Issue が複数レイヤーに跨がることは普通にある）

  • フロントエンド — apps/*/expo_frontend、apps/lp_app の画面・配線
  • バックエンド — apps/functions（Cloud Functions）、apps/backend（Dart / Cloud Run）、apps/admin_app/node_backend
  • 共通モジュール — shared/ 配下。フロント共通コンポーネント・ドメインサービス・共通ロジック
  • データ層 — infrastructure/firebase/firestore/firestore.rules、インデックス定義、スキーマ移行
  • CI・リリース基盤 — scripts/、githooks/、.github/workflows、tests/、ビルド設定
  • ドキュメント・仕様 — docs/、spec/、.claude/skills/

6. 要判断・未対応の 4 件

#781 / #782 / #784 / #785 は修正コミットを伴わない調査報告と方針提案です。いずれも shared/ の構造課題で、 spec/ の正典化（#778）で仕様を書き起こす過程で表面化しました。

  • #781 passkeyLinking.tsx — モックのチャレンジとハードコード rp.id のまま。実経路からは呼ばれておらず実害はないが、「実装済みの関数がある」と誤認して配線すると事故になる。削除するか、実経路の実装へ置き換えるかの判断待ち。
  • #782 core/utils のドメインサービス混在 — MatchingService や SelectionStateMachine といった中核ルールが utils という名前に埋もれ、新規ファイルの置き場所を決められない。再編は影響範囲が広くリスクだけがあるため、当面は仕様側で区分を明示する案。
  • #784 NotificationService の 2 実装併存 — 宛先フィールドが uid と userId で食い違い、通知が届かない経路が生じうる。認可が node_backend と adminGuard の 2 系統あった問題（#771 で解消）と同型。実データの分布調査が先行して必要。
  • #785 shared/utils の削除提案 — 0 行の空ファイルとテスト用ダミーのみで参照ゼロ。実体の無いモジュールが spec/coverage-map.json の分母に入り、仕様網羅率が実態を表さなくなる。

7. この分類の作り方

Issue 番号を変えて同じ集計を繰り返せるよう、判定は次の順序で機械的に行っています。

  • ① 対象の抽出 — gh issue list --repo yama-0t0k0/forAgent --state all --json number,title,labels,body で取得し、指定番号以降を対象にする。タイトルが chore: Agent ブランチ最新化と same へのマージ・main 最新化 で始まるものはブランチ同期作業として除外。
  • ② パス抽出 — Issue 本文の「変更ファイル」節に列挙されたパスを取り出す（節が無い場合は本文全体から）。
  • ③ アプリ／レイヤー判定 — apps/<app>/expo_frontend → そのアプリのフロントエンド、apps/functions → Cloud Functions、shared/** → 共通モジュール、infrastructure/firebase と tests/security_rules → データ層、scripts/・githooks/・.github/ → CI・リリース基盤、docs/・spec/ → ドキュメント・仕様、という先頭一致で写像する。
  • ④ 人手での検証 — ③だけでは「変更ファイル節が無い Issue」「調査報告のみで変更を伴わない Issue」「撤去済みディレクトリ（apps/admin_app/node_backend）を指す Issue」を取りこぼすため、全件の本文を読んで補正する。
